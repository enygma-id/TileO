# Remote Storage and S3-Compatible Inputs

TileO can inspect and process supported data from **public or presigned HTTPS URLs** and from configured **S3-compatible object storage connections**. Access patterns depend on the object's format, version-pinning, connection policy, and remote-staging limits. Processing is initiated by a user or API job; this document does **not** describe a built-in periodic bucket synchronizer.

## 1. Public or presigned URL

Use a URL generated by the storage operator, ideally short-lived and read-only. Paste or submit it through the supported URL-input workflow. TileO performs URL validation and may stage the input locally before processing. Remote reads depend on version and range-read requirements; an expired, changed, unreachable or disallowed URL will fail.

Do not put presigned URLs into issue reports, screenshots or documentation. They may embed credentials. The application has specific host/URL validation and credential-redaction controls; operators must still configure a safe network boundary.

## 2. S3-compatible connections

A TileO deployment may be configured with permitted S3 connections in its runtime configuration. Depending on the connection, access can use operator-provided credentials, configured server credentials or supported AWS temporary credentials. Limit permissions to the intended objects and prefixes, normally `s3:GetObject` and, where required, `s3:ListBucket` or version operations.

Configuration may include a provider endpoint, region, bucket allowlist, prefix restrictions, connection ID and whether direct remote reading is allowed. A source may be **staged** to local scratch or read through a restricted remote path when its conditions permit. Check the current [API](../API.md), [OpenAPI spec](../openapi.yaml), [installation](INSTALLATION.md), and runtime `.env.example` for the supported fields.

**Security:** avoid root/admin storage keys. Do not paste secrets into public documents or commit them to Git. Store actual credentials using deployment-approved secret management and follow the application's storage credential setup.

## 3. AWS IAM roles

IAM role integration must be configured by the operator. In particular, AWS account information is not inferred automatically: the implementation disables this integration when `TILEO_AWS_ACCOUNT_ID` is unset. Review role ARN, external ID, trust policy and permissions against the deployment account actually being used. TileO is self-hosted; do not assume an Enygma-hosted account is supplying credentials for your installation.

## 4. Operational limitations

- No built-in recurring bucket polling/scheduled reconversion is promised here.
- Remote URL/object inspection, staging and native-tool access may have separate size, network and resource limits.
- S3 object versioning, ETag validation and remote-read eligibility depend on the configured source and workflow.
- Source data owners remain responsible for rights to process and redistribute outputs.

See [Operations](OPERATIONS.md) for backups, security and deployment; [Tools](TOOLS.md) for GDAL, and [Release Process](RELEASE_PROCESS.md) for verifying actual production behavior.
